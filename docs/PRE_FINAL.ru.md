## Что объединено

Ветка объединяет `feature/wind-power-baseline` на коммите `e3455465897a6e9ef84b7963404cf4b5ae0dcba6` и `yevgeniy` на коммите `d34ac600506a974bdf1e71b72e672fe89cacd96a`. Для этого не требуется менять `main` или исходные ветки. Выбранные веса модели сохранены без изменений.

Django отвечает за интерфейс, авторизацию, получение погоды, неизменяемые снимки, историю прогнозов, валидацию, обновление и экспорт. Отдельный FastAPI-процесс загружает включённую в репозиторий NumPy-модель и преобразует 48 часов прогноза JMA GSM в нормализованную мощность. Обучение, GPU и ключи NVIDIA для работы системы не нужны.

```text
Браузер / авторизованный API-клиент
  -> Django (web:8000, на хосте localhost:18080)
     -> GET windpower-ml:8000/v1/metadata
     -> Open-Meteo JMA GSM по координатам выбранной турбины
     -> проверка единиц, высот, часов и значений; сохранение снимка
     -> POST windpower-ml:8000/v1/predict
     -> проверка ответа/версии; история, анализ, отображение и экспорт
```

Найдена и исправлена блокирующая несовместимость metadata: модель возвращает `supported_weather_models` и `fields`, а веб-адаптер ожидал `weather_model` и `field_definitions`. Адаптер теперь понимает фактический контракт и сохраняет поддержку явно заданных старых имён. Диапазоны признаков в Django приведены к ограничениям модели. Режим по умолчанию — HTTP-инференс; синтетическая погода в нём скрыта в интерфейсе и отклоняется сервером.

## Запуск в Docker

Нужны Git, Python 3.12+ для генерации конфигурации, Docker Compose v2 и запущенный движок Linux-контейнеров. Используйте **отдельную копию pre-final**, чтобы не мешать работе над main. Не переключайте ветку в каталоге, который использует другой процесс.

```sh
git clone --branch pre-final https://github.com/BAITC-Hacks/hack-15d1fa83-team.git windpower-pre-final
cd windpower-pre-final
python deployment/configure.py
docker compose config --quiet
docker compose up --build -d
docker compose ps
docker compose exec web python manage.py createsuperuser
```

Для клонирования нужен доступ к закрытому репозиторию. `createsuperuser` предложит выбрать логин и пароль; готового общего пароля нет. Откройте **http://localhost:18080**, войдите, выберите турбину и Open-Meteo, затем постройте live-прогноз. Переключатель 24/48 часов меняет отображение; модель всегда получает 48 часов.

`configure.py` использует только стандартную библиотеку Python. Скрипт создаёт `.env` со случайными `DJANGO_SECRET_KEY`, `API_TOKEN`, `ML_SERVICE_TOKEN`, именем проекта и портом. Секреты не выводятся в консоль. Существующий файл не перезаписывается: при повторном запуске сохраните уже созданный `.env`. Compose читает его автоматически; обычные команды Python/Django — нет.

Зависимости разделены по образам: `Dockerfile` устанавливает зафиксированный ML runtime, `Dockerfile.web` — Django, requests, Waitress и WhiteNoise. Оба процесса работают от непривилегированного пользователя. В образы не входят PyTorch, CUDA, исходные CSV или задания обучения. `.dockerignore` допускает только необходимые исходники и модель.

ML доступен внутри Compose по `http://windpower-ml:8000/v1/predict`; порт 8001 на хост **не** публикуется. Веб-порт — **127.0.0.1:18080**. Имя проекта **windpower-pre-final** отделяет контейнеры, сеть и том БД от других запусков. Фиксированных имён контейнеров нет. Если порт занят, измените `WEB_PORT` в `.env`.

При запуске веб-сервис выполняет миграции, `seed_demo`, `collectstatic`, затем запускает Waitress. Несмотря на старое имя, `seed_demo` создаёт только две реальные турбины с координатами; синтетические прогнозы не создаются, существующие настройки турбин не перезаписываются. WhiteNoise отдаёт CSS/JS при выключенном debug. SQLite сохраняется в отдельном томе проекта.

```sh
docker compose logs --tail=100 web windpower-ml
docker compose stop
docker compose start
# Удалить контейнеры и сеть этого проекта, сохранив БД:
docker compose down
```

`down -v` удалит сохранённую БД. Для публикации в интернете нужны HTTPS reverse proxy, разрешённые домены, secure cookies и перенаправление на HTTPS; текущая конфигурация предназначена для локального HTTP. `API_TOKEN` нужен внешним клиентам Django API, `ML_SERVICE_TOKEN` — общению Django с моделью. Это разные секреты, ни один из них не является ключом NVIDIA. Браузер использует Django-сессию и CSRF-защиту.

## Запуск без Docker и проверки

Рекомендуется Python 3.12 и новое окружение, отдельное от уже работающих копий:

```sh
python -m venv .venv
# Windows PowerShell:
.venv\Scripts\Activate.ps1
# В Linux вместо предыдущей команды: source .venv/bin/activate
python -m pip install -r requirements-runtime.txt -r requirements.txt -e .
python -m pip check
python deployment/verify_stack.py --live --report reports/local-stack.json
```

Проверка запускает два настоящих HTTP-сервиса на свободных локальных портах, использует случайные секреты и временную БД, проверяет обе турбины и останавливает только собственные процессы. `--live` получает текущую погоду JMA. Без этого флага проверяются запуск, metadata, авторизация, статика и инференс настоящей модели на контрольных запросах без запроса погоды. Время выпуска не выдумывается. Временная история после проверки удаляется; сборка статики создаёт `staticfiles/` в этой копии.

Для интерактивной разработки запустите `python inference/serve.py --allow-provisional --port 18081` в одном терминале. Во втором терминале с активированным окружением:

```powershell
$env:ML_BACKEND = 'http'
$env:ML_SERVICE_URL = 'http://127.0.0.1:18081/v1/predict'
python manage.py migrate
python manage.py seed_demo
python manage.py runserver 127.0.0.1:18080
```

Этот пример использует настройки Django для разработки, включая debug, и предназначен только для локального доступа. Если задан `ML_SERVICE_TOKEN`, он должен совпадать в обоих терминалах. Для запуска с выключенным debug и обязательной авторизацией используйте профиль Docker выше.

Полный набор тестов требует CPU PyTorch для небольших тестов обучения:

```sh
python -m pip install torch --index-url https://download.pytorch.org/whl/cpu
python -m pip install -e '.[test]'
python manage.py check
python manage.py makemigrations --check --dry-run
pytest -q
```

## Интерфейсы и ответственность

| Интерфейс | Назначение |
|---|---|
| Web `POST /api/v1/forecasts/` | Тело `{"turbine_id":"turbine_1","mode":"live","provider":"open_meteo"}`; для второй точки замените ID на turbine_2 |
| Web `GET /api/v1/ml/metadata/` | Актуальные возможности загруженной модели в нормализованном виде |
| Web `GET /api/v1/forecasts/<id>/` | Сохранённые результат, погода, происхождение, этапы и предупреждения |
| Web `POST /api/v1/forecasts/<id>/refresh/` | Повторное получение погоды и расчёт с сохранением истории |
| Web `GET /api/v1/forecasts/<id>/export.csv` | 48 прогнозов и строка заголовка |
| Web `GET /api/v1/forecasts/<id>/ml-input/` | Точный запрос, переданный модели |
| ML `GET /health` | Публичная проверка работоспособности |
| ML `GET /v1/metadata`, `POST /v1/predict` | Межсервисный интерфейс с токеном |

Документы: [OpenAPI Django](dashboard-openapi.json), [OpenAPI ML](openapi.json), [схема входа](ml-input.schema.json), [схема выхода](ml-output.schema.json), [контракт интеграции](ML_INTEGRATION.md), [погода и replay](WEATHER_ARCHIVE.md). Два OpenAPI описывают разные серверы.

| Турбина | Широта | Долгота |
|---|---|---|
| turbine_1 | 43.645150 | 78.535604 |
| turbine_2 | 43.643198 | 78.538828 |

Для каждой турбины используются собственные координаты и ID модели. В близких точках сеточная погода может быть похожей, но идентичность турбин не смешивается. Признаки: ветер 10 м в м/с (0–100), направление ветра 10 м ОТ севера по часовой стрелке в градусах (0–360), температура 2 м в °C (-100–70), 48 последовательных целых часов UTC. Ветер 100 м не нужен. Выход — нормализованная мощность [0,1], не МВт; перевод в физические единицы требует подтверждённой номинальной мощности и определения нормировки.

Оркестрация детерминирована: LLM для принятия решений и постоянно работающего планировщика здесь нет. `python manage.py refresh_forecasts --limit 20` выполняет один проход по сохранённым успешным окнам; регулярность задаётся внешним планировщиком. Live-обновление использует текущее серверное время и погоду, replay сохраняет исторический момент решения. Перед использованием кэша заново запрашивается metadata. При сбоях нет подмены синтетикой, другой погодной моделью или фиктивной мощностью.

## Результаты проверки и ограничения

23.09.2026 прошли **93 теста и 31 подтест**. `pip check` не нашёл конфликтов, Django-проверки успешны, пропущенных миграций нет. Настоящий двухсерверный HTTP-тест с выключенным debug и авторизацией получил live-погоду JMA для обеих точек, сформировал по 48 часов, сохранил и экспортировал результаты. Прогнозы точно совпали с прямыми ответами модели. См. [live-отчёт](../reports/pre-final-live.json) и [сводку](../reports/pre-final-verification.json).

Конфигурация Compose прошла валидацию. Docker Engine недоступен на проверявшем компьютере, поэтому сборка образов, выполнение Linux-контейнеров и права томов **ещё не проверены запуском**. Полный набор тестов настроен в GitHub Actions; локальный успех не означает подтверждённый успех удалённого CI.

`alignment_confirmed=false` сохранён честно: нужно подтвердить, означает ли время измерения начало или конец интервала. Выбранная MSE-модель не переобучалась; тест интеграции не доказывает повышение точности. Метрики на отложенных данных описаны в README модели.

Для live неизвестное время выпуска/доступности погоды остаётся null. Replay через Previous Runs использует фиксированные заблаговременности и оценочное время доступности с явными предупреждениями. Строгий конкурсный replay требует подтверждённого происхождения архивных выпусков; оценка на фактических февральских данных остаётся отдельной работой. Успешная интеграция не доказывает точность или историческую доступность прогноза.
